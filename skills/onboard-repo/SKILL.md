# onboard-repo - write a repo's profile

The factory works on repos that live beside it: `../{dir}` from the factory root. Each needs `repos/{dir}.md`.

1. **Find it.** Confirm `../{dir}` exists and is a git repo with a GitHub remote: `git -C ../{dir} remote get-url origin`. Not cloned yet: ask the person to clone it beside the factory.
2. **Read, don't guess.** From the repo: its `AGENTS.md` / `CLAUDE.md` / `CONTRIBUTING.md`, `package.json` scripts or `Makefile` / `pyproject.toml` / `Cargo.toml`, the CI workflows in `.github/workflows/`, and `gh repo view {owner}/{name} --json defaultBranchRef,mergeCommitAllowed,squashMergeAllowed,rebaseMergeAllowed`. Check branch protection for required checks if you can: `gh api repos/{owner}/{name}/branches/{branch}/protection`.
3. **Fill the profile.** Copy [the repo template](../../_templates/repo.md) to `repos/{dir}.md` and fill every field. A command the repo lacks is `none`, never invented. `default_branch` is the branch PRs should target; `merge_method` must be one the repo allows. `release_branch` is the production branch a release merges into, or `none` if the factory shouldn't release; when set, fill `release_head` and every `## Release` line from the repo's own release guide and deploy workflow: each repo releases differently, and that section is the whole recipe. Add protected paths the repo needs (migrations, infra, release config). Under Notes put what an agent would get wrong: branch rules, never-touch areas, how issues get closed.
4. **Prove the commands.** Run install, lint, typecheck, test and build once in the repo (or a throwaway worktree) and note any that fail on the base branch: the factory will stop on those.
5. **Dev container.** If `../{dir}/.devcontainer/devcontainer.json` exists, leave it. If not, write one from what step 2 found, never guessed: `name` is `{dir}`; `image` is the official image for the repo's runtime, pinned to the version the repo already declares (`packageManager`, `engines`, `.nvmrc`, `.tool-versions`, `.python-version`), e.g. `oven/bun:1.3.14`; the `ghcr.io/devcontainers/features/git:1` feature; `containerEnv` `DEVCONTAINER: "true"`; the dev server's port in `forwardPorts`; the profile's install command as `postCreateCommand`. Services (Postgres, Redis) go in through `dockerComposeFile` only when the repo already has a compose file for them: list that file first and `.devcontainer/docker-compose.yml` second. The second adds an `app` service (the image, `command: sleep infinity`, `network_mode: service:<db>`, the repo mounted at `/workspaces/{dir}`), puts every other service on `network_mode: service:<db>` too, and drops host ports with `ports: !reset []` (and a fixed `container_name` with `!reset null`), so the `.env` localhost URLs work unchanged and nothing clashes with the host's own stack. Give it a top-level `name: {dir}-devcontainer` so it never takes over the repo's running compose project. Relative paths in it resolve from the first compose file's folder, not `.devcontainer/`. A runtime the image lacks (Node beside Bun) goes in a two-line `.devcontainer/Dockerfile`, as the repo's CI or Dockerfiles already pair them. Prove it in a fresh clone with the files added (`git clone ../{dir} <tmp>`: not a worktree, whose `.git` points outside the container, and with no `node_modules`, since a host install breaks the container's): `npx -y @devcontainers/cli up --workspace-folder <tmp>` must finish its `postCreateCommand`; run the repo's lint on the new files and its tests inside; then `docker compose -p <project> down -v` and delete the clone. Don't commit the CLI's `devcontainer-lock.json`. Commit on a `chore/devcontainer` branch in the repo's own commit style and `gh pr create` against `default_branch`; the person merges it. If they use DevPod (`devpod list` shows workspaces), once they've pulled the merge, add it like theirs: delete the checkout's `node_modules`, `devpod up ../{dir} --id {dir} --provider <theirs> --ide <theirs> --open-ide=false`, then run the install command on the host again, because the folder's `node_modules` is shared.
6. **Show the person** the profile and the dev container PR, and ask about `auto_merge`: `true` lets the approver merge when the gate holds; `false` always asks them. They approve before you're done.
7. The factory creates its labels in the repo on the first `pull` or `new`. Point them at the [new-task](../new-task/SKILL.md) skill.

This skill writes into `repos/`, which stage agents may never edit, and opens a PR in the repo. Run it only in a session with the person, never from a stage.
